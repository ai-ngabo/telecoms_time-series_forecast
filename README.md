# Comparative Analysis of Sequential Models for Mobile Network Traffic Forecasting

Machine Learning Techiniques I assignment: one-step-ahead forecasting of mobile Internet traffic across
Milan, using the Telecom Italia MI2 dataset (Nov-Dec 2013, 10,000 grid areas,
10-minute resolution). Three models are implemented and compared: SARIMA, GRU,
and LightGBM.

Full findings and discussion are in the report. This README covers
environment setup and exact reproduction steps.

## Data

Raw data: Telecom Italia "MI2" dataset, tab-separated `.txt` files, one per day,
no header row. Columns: `square_id, time_interval_ms, country_code, sms_in,
sms_out, call_in, call_out, internet_traffic`.

- Source: https://doi.org/10.7910/DVN/EGZHFV (Harvard Dataverse; a short
  Guestbook form is required before download)
- Place the November and December 2013 files under `telecom_italia/`, split into
  `data_2013_november/` and `data_2013_december/` subfolders (any file
  matching `sms-call-internet-mi-*.txt` anywhere under `telecom_italia/` is
  discovered automatically, regardless of subfolder).
- The raw data is **not committed to this repository** (the full two-month
  collection is ~19 GB). Only the processed, aggregated Parquet output is
  small enough to consider committing, and even that is regenerated by the
  pipeline below rather than checked in.

## Reproducing the full pipeline

Run every command below from the project root, in this exact order.

### 1. Memory-management evidence (Section: Dataset and Data Preparation)

```bash
python scripts/baseline.py telecom_italia/data_2013_november/sms-call-internet-mi-2013-11-01.txt
python scripts/optimized_baseline.py telecom_italia/data_2013_november/sms-call-internet-mi-2013-11-01.txt
```
Writes `tables/baseline_result.json` and `tables/optimized_baseline_result.json`
(peak memory, in-memory size, row counts, before vs. after).

### 2. Full dataset build (all 61 day-files -> one wide matrix)

```bash
python scripts/batch_pipeline.py telecom_italia processed_data
```
Discovers every raw day-file under `telecom_italia/`, processes each one
(chunked read, column selection, dtype downcasting, country-code
aggregation), and combines them into `processed_data/full_wide_matrix.parquet`
(shape `(8784, 10000)`, Nov-Dec 2013 only - the January 1st file, if present
in your download, is excluded automatically; see the report's Dataset section
for why).

This step processes ~19 GB of raw text and can take several minutes. If it is
interrupted after the per-day processing has already completed, you do not
need to redo that part -- rerun with `--combine-only` to skip straight to the
final combination step:
```bash
python scripts/batch_pipeline.py telecom_italia processed_data --combine-only
```

### 3. Exploratory analysis (Section: Exploratory Analysis)

```bash
python scripts/exp_data_analysis.py processed_data/full_wide_matrix.parquet
```
Produces `figures/fig1_traffic_distribution.png` through `fig4_stl_decomposition_top_area.png`,
and prints the top-3 areas, distribution stats, and ADF stationarity results
also reported in `tables/`.

### 3b. Spatial analysis (Figure 2 in the report)

Requires the Milan grid cell boundaries, downloaded separately from the main
activity data:
- Source: https://doi.org/10.7910/DVN/QJWLFU (Harvard Dataverse; a short
  Guestbook form is required)
- Download the GeoJSON file and place it at
  `telecom_italia/data_milano_grid/milano-grid.geojson`

```bash
python scripts/spatial_analysis.py processed_data/full_wide_matrix.parquet telecom_italia/data_milano_grid/milano-grid.geojson
```
Joins total traffic per area to the grid's `cellId` field (matches
`square_id` directly), and produces `figures/fig6_spatial_traffic_map.png` --
a choropleth of total traffic across Milan with the top-3 areas and the
Duomo (city centre) annotated, plus `tables/spatial_top3_distances.json`
(each top-3 area's distance in metres from the city centre).

### 4. Shared data preparation for forecasting (Section: Methodology)

```bash
python scripts/data_prep.py processed_data/full_wide_matrix.parquet
```
Builds the windowed, scaled train/test arrays (`processed_data/windows_<area>.npz`)
used identically by all three models: temporal split (train through 15 Dec,
test 16-22 Dec), window length p=144, MinMax scaling fit on train only.

### 5. Hyperparameter tuning (Section: Methodology -- documented per the brief's requirement)

```bash
python scripts/tune_sarima.py processed_data 5161
python scripts/tune_lgbm.py processed_data 5161
python scripts/tune_gru.py processed_data 5161
```
Each writes a `tables/<model>_tuning_log.csv` (every configuration tried) and
a `tables/<model>_..._summary.json` (the selected configuration and reasoning).

### 6. Train and evaluate all 3 models, for all 3 areas

```bash
for area in 5161 5059 5259; do
    python scripts/sarima.py processed_data $area
    python scripts/gru.py processed_data $area
    python scripts/lgbm_model.py processed_data $area
done
```
Each writes `tables/<model>_<area>_result.json` (metrics, timing) and
`processed_data/<model>_preds_<area>.npz` (predictions, for plotting).

### 7. Assemble final results (Section: Results and Discussion)

```bash
python scripts/assemble_results.py processed_data
```
Produces the 3 per-area metric tables, the timing table, the 9-panel
actual-vs-predicted figure (`figures/fig5_actual_vs_predicted_grid.png`), and
the weekend-vs-weekday failure-case analysis table -- everything reported in
the Results and Discussion section of the report.

## Hardware used for reported timing figures

HP EliteBook x360 1030 G2, Intel Core i7-7600U (2 physical cores / 4 logical
threads, 2.80 GHz), no dedicated GPU, Windows 11 Pro. Absolute timing numbers
will differ on other hardware; the relative pattern (LightGBM fastest, GRU
slowest to train but fast to infer, SARIMA fast to train but slow to infer due
to its walk-forward evaluation loop) should be representative regardless of
machine.

## Limitations

See the report's Conclusion and Future Work section for the full discussion.
In brief: hyperparameter tuning was performed on a single area (5161) and
applied to all three; SARIMA's seasonal-differencing formulation captures
daily but not weekly seasonality; the forecasting task is univariate
(SMS/call volume are present in the raw data but not used); evaluation
covers three areas and one test week.
